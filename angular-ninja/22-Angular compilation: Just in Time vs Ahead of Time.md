#### Компиляция Angular: Just in Time против Ahead of Time

#### 22.1. Генерация кода

В предыдущей главе мы кратко упомянули о том, как фреймворк генерирует функцию обнаружения изменений для каждого компонента.

Это очень интересный и особенный нюанс Angular, которого вы не увидите в других фреймворках: Angular при запуске вашего приложения компилирует шаблоны и генерирует динамический код для каждого компонента.

HTML, который вы пишете в своих шаблонах, никогда не читается браузером напрямую. Вместо этого Angular генерирует определение компонента (*component definition*) для каждого компонента, точно отражающее то, что вы написали в шаблоне.

Это определение компонента встраивается (*inline*) в статическое поле класса вашего компонента.

Давайте рассмотрим пример с нашим хорошо знакомым Pony. Шаблон состоит в основном из изображения с привязанным свойством источника и элемента `<figcaption>` с интерполяцией:

```html
<figure>
  <img [src]="ponyImageUrl()">
  <figcaption>{{ ponyModel().name }}</figcaption>
</figure>

```

Когда Angular компилирует это, он сначала парсит шаблон для создания так называемого абстрактного синтаксического дерева (**AST** — *Abstract Syntax Tree*). AST — это дерево, представляющее структуру шаблона, которое обычно используется компиляторами для подобных целей. Это результат этапа синтаксического анализа компиляции.

Затем это AST используется для генерации динамического кода JavaScript — «определения компонента» для каждого компонента, которое встраивается в статическое поле класса компонента.

Определение компонента содержит несколько вещей, и среди них — шаблон, представленный функцией:

```javascript
domElementStart(0, 'figure');{
  domElement(1, 'img');}{
  domElementStart(2, 'figcaption');
  text(3);
  domElementEnd();}
domElementEnd();

```

> В этой главе описывается код, генерируемый компилятором/рендерером, представленным в Angular 8.0 под названием **Ivy**.
> Этот рендерер является третьей итерацией (первоначальный рендерер был переписан еще в Angular 4.0). Эти итерации принесли либо повышение производительности, либо уменьшение размера бандла, либо и то, и другое, сохраняя при этом тот же синтаксис шаблонов, обеспечивая обратную совместимость с существующим кодом и позволяя разработчикам очень легко мигрировать.

С помощью этой функции Angular может создать DOM, соответствующий нашему Pony: по сути, он добавляет соответствующий `HTMLElement` в DOM для каждого элемента.

Но как он обрабатывает обнаружение изменений? Функция шаблона на самом деле немного длиннее:

```typescript
template: (renderFlags: RenderFlags, component: Pony) => {
  if (renderFlags & RenderFlags.Create) {
    domElementStart(0, 'figure');
    {
      domElement(1, 'img');
    }
    {
      domElementStart(2, 'figcaption');
      text(3);
      domElementEnd();
    }
    domElementEnd();
  }
  if (renderFlags & RenderFlags.Update) {
    advance();
    domProperty('src', component.ponyImageUrl());
    advance(2);
    textInterpolate(component.ponyModel().name);
  }
},

```

Эта функция шаблона состоит из двух частей:

1. **Создание компонента**, которое описано выше.
2. **Обновление компонента**, которое делает по сути то же самое, что вы написали бы вручную (т. е. изображение имеет свойство `src`, отражающее результат работы метода `ponyImageUrl()` компонента, а `figcaption` содержит текст, отражающий имя пони).

Она вызывается фреймворком каждый раз, когда требуется проверить наличие изменений. По сути, функция получает значения динамических частей (атрибут `src` и интерполяцию), а затем вызывает функцию фреймворка с индексом элемента для обновления и другую функцию с его свойством и новым значением.

Затем фреймворк сравнивает предыдущее значение, сохраненное для этого элемента, и, если оно изменилось, обновляет его и заменяет новым значением.

Этот сгенерированный код работает очень быстро и может быть оптимизирован JS-движками (см. раздел о мономорфизме и инлайн-кешировании в предыдущей главе).

Генерация кода занимает некоторое время, поэтому раньше она выполнялась прямо в браузере при запуске приложения. Этот режим назывался компиляцией «на лету» — **Just in Time (JiT)**.

Компилятор Ivy теперь достаточно быстрый, чтобы выполнять эту компиляцию непосредственно во время выполнения `ng serve` или `ng build`. Этот режим называется компиляцией «наперед» — **Ahead of Time (AoT)**, и он подробно описан ниже.

**Подводя итог, когда вы используете JiT-компиляцию:**

* Вы пишете код на TypeScript и шаблоны HTML;
* Вы компилируете TypeScript в JavaScript и отправляете JS и HTML вашим пользователям;
* Во время выполнения (runtime) HTML также компилируется в JS-код.

#### 22.2. Компиляция Ahead of Time (AoT)

Мы можем сгенерировать этот код до запуска приложения, используя компилятор, написанный командой Angular — компилятор **Ahead of Time (AoT)**.

Вы можете вызвать его вручную в своем проекте (`ngc`) или, если вы используете Angular CLI, он включен по умолчанию при запуске `ng serve` или `ng build` (начиная с Angular CLI v8.1).

Сборка использует компилятор Angular для компиляции шаблонов в файлы TypeScript.

В TypeScript? Да, потому что это позволяет убедиться, что мы не допустили ошибок в наших шаблонах!

Сгенерированный код TypeScript и код нашего приложения затем компилируются компилятором TypeScript (`ngc` сразу же вызовет компилятор TypeScript), и если вы допустили ошибку в шаблоне, вы увидите ошибку:

```html
<figure>
  <!-- неправильное имя вызываемого метода -->
  <img [src]="ponyImageUr()">
  <figcaption>{{ ponyModel.name }}</figcaption>
</figure>

```

Компилятор Angular сгенерирует следующий код TypeScript:

```typescript
// ...
// опечатка в вызове метода в сгенерированном коде
domProperty('src', component.ponyImageUr());
advance(2);
textInterpolate(component.ponyModel().name);

```

что вызовет ошибку при компиляции TypeScript:

```text
Property 'ponyImageUr' does not exist on type 'Pony'.

```

Это отлично, потому что означает, что вы можете проверить все свои шаблоны еще до запуска приложения. Ваши будущие рефакторинги пройдут безболезненно: если вы переименуете метод или свойство в компоненте, вы сразу узнаете, что шаблон также необходимо обновить, поскольку в противном случае сборка сломается.

Это также означает, что такая компиляция может выдать ошибку там, где ваш код нормально работал бы в режиме Just in Time. Например, если у вас есть приватное свойство `private input` в компоненте, в режиме JiT все будет в порядке (поскольку в JavaScript нет понятия приватных свойств класса на уровне синтаксиса, доступных только в TS), но в режиме AoT сборка сломается (так как сгенерированный TypeScript-код другого компонента должен получить доступ к этому свойству).

Компиляция приложения перед отправкой пользователям также значительно ускорит запуск приложения, поскольку компиляция уже будет выполнена!

**Подводя итог, в режиме AoT:**

* Вы по-прежнему пишете на TypeScript и HTML;
* Вы компилируете HTML в TypeScript, а затем весь код TypeScript — в JavaScript;
* Вы отправляете только итоговый JS-код вашим пользователям.

Минусом будет размер бандла JavaScript, который вы отправляете пользователям: сгенерированный код больше, чем нескомпилированные шаблоны.

Это отчасти компенсируется тем, что вам не нужно поставлять сам компилятор Angular пользователям, так как шаблоны уже скомпилированы. А компилятор — это довольно большой объем кода, так что это хорошая экономия.

В средних и крупных приложениях это, как правило, не полностью перекрывает увеличение размера сгенерированного кода. Если вы хотите получить все плюсы AoT-компиляции и при этом маленький бандл, вам нужно будет изучить функцию ленивой загрузки (*lazy-loading*), которую мы объясняли в главе про Router.
