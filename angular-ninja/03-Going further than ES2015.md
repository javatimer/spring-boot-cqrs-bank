
### Выходя за рамки ES2015+

### 3.1. Динамическая, статическая и опциональная типизация

Возможно, вы слышали, что приложения на Angular можно писать на TypeScript. И, скорее всего, задаётесь вопросом, что такое TypeScript и какие преимущества он даёт.

JavaScript обладает динамической типизацией. Это означает, что вы можете делать подобные вещи:

```javascript
let pony = 'Rainbow Dash';
pony = 2;

```

И это работает. Это удобно во многих случаях, так как вы можете передать практически любой объект в функцию, и всё будет работать — до тех пор, пока у объекта есть свойства, необходимые этой функции:

```javascript
const pony = { name: 'Rainbow Dash', color: 'blue' };
const horse = { speed: 40, color: 'black' };
const printColor = animal => console.log(animal.color);

// работает, пока у объекта есть свойство `color`

```

Эта динамическая природа открывает замечательные возможности, но также создает ряд проблем по сравнению со статически типизированными языками. Самая очевидная: когда вы вызываете неизвестную функцию в JS из внешнего API, вам практически всегда приходится читать документацию (или, что ещё хуже, исходный код функции), чтобы понять, как должен выглядеть параметр.

Посмотрите на предыдущий пример: методу `printColor` нужен параметр со свойством `color`. Об этом бывает трудно догадаться, а в повседневной работе всё ещё сложнее, ведь мы используем множество библиотек и сервисов, написанных другими разработчиками.

Один из сооснователей Ninja Squad часто жалуется на отсутствие типов в JS и искренне сожалеет, что не может быть столь же продуктивным и писать настолько же качественный код, как в статически типизированной среде. И он не так уж прав относительно причин своей ругани, но суть улавливает верно!

Без информации о типах среда разработки (IDE) понятия не имеет, делаете ли вы что-то не так, а инструменты статического анализа не могут помочь вам найти баги в коде. Разумеется, у нас есть тесты, а Angular всегда стремился сделать тестирование простым, но достичь идеального покрытия тестами практически невозможно.

Это подводит нас к теме поддерживаемости кода. JS-код может стать сложным в поддержке, несмотря на тесты и документацию. Рефакторинг огромного JS-приложения — далеко не простая задача по сравнению с тем, как это делается в статически типизированных языках. Поддерживаемость — важнейший фактор, а типы помогают и людям, и инструментам избегать ошибок при написании и сопровождении кода.

Компания Google всегда стремилась продвигать новые решения в этом направлении. Это легко понять: они владеют одними из крупнейших веб-приложений в мире (GMail, Google Docs, Maps…), поэтому опробовали множество подходов к поддерживаемости фронтенда — GWT, Google Closure, Dart… Все они создавались для облегчения разработки крупных веб-приложений.

Для Angular команда Google хотела помочь нам писать более качественный JS, добавив в код информацию о типах. Это не совсем новая концепция для JS — когда-то типы даже были предметом спецификации ECMAScript 4, от которой позже отказались.

Сначала они анонсировали **AtScript** как надмножество ES2015+ с аннотациями (аннотациями типов и ещё одним видом аннотаций, о котором поговорим позже). Также они объявили о поддержке **TypeScript** — языка от Microsoft с дополнительными аннотациями типов. А спустя несколько месяцев команда TypeScript объявила о тесном сотрудничестве с Google, отметив, что новая версия языка (1.5) будет содержать все фичи AtScript. После этого Google официально закрыла AtScript, объявив TypeScript новым главным стандартом для разработки приложений на Angular!

### 3.2. Появление TypeScript

Я считаю, что это было очень умным ходом по нескольким причинам.

Во-первых, никто на самом деле не хочет учить ещё одно расширение языка. А TypeScript к тому моменту уже существовал, обладая активным сообществом и экосистемой. Я не использовал его до Angular, но слышал о нём много хорошего от самых разных людей.

TypeScript — это проект Microsoft. Но это не та Microsoft периода Балмера и Гейтса, о которой вы могли подумать. Это Microsoft эпохи Наделлы — открытая для сообщества и опенсорса. В Google это понимают, и для них куда выгоднее вкладываться в существующий проект, чем брать на себя бремя поддержки собственного. В итоге фреймворк TypeScript получил колоссальный буст популярности — ситуация "win-win", как сказал бы ваш менеджер.

Но главная причина сделать ставку на TypeScript — это предлагаемая им система типов. Это **опциональная** система типов, которая помогает, не вставая на пути. На самом деле, поработав с ней какое-то время, вы, скорее всего, захотите писать на TypeScript абсолютно все свои приложения. Мне очень нравится то, что они сделали, и в следующем разделе мы подробно разберем возможности TS. В итоге у вас будет достаточно знаний, чтобы читать любой Angular-код и осознанно решить, использовать ли его в своих проектах.

Вы можете спросить: зачем использовать типизированный код именно в Angular-приложениях?
Давайте рассмотрим пример. Angular построена вокруг мощной концепции под названием **«внедрение зависимостей» (Dependency Injection, DI)**. Вы уже можете быть знакомы с ней, так как это распространенный паттерн проектирования во многих фреймворках и языках, который применялся ещё в AngularJS 1.x.

### 3.3. Практический пример с DI (Dependency Injection)

Чтобы кратко объяснить суть внедрения зависимостей, представьте компонент приложения — скажем, `RaceList`, которому нужен доступ к списку гонок, предоставляемому сервисом `RaceService`.

Вы могли бы написать `RaceList` следующим образом:

```javascript
class RaceList {
  constructor() {
    this.raceService = new RaceService();
    // предположим, что list() возвращает промис
    this.raceService
      .list()
      // сохраняем полученные гонки в поле класса `RaceList`
      .then(races => (this.races = races));
    // стрелочные функции рулят!
  }
}

```

Но у такого подхода есть несколько недостатков. Один из них — **тестируемость**: теперь очень сложно подменить `raceService` на фейковый объект (mock), чтобы протестировать наш компонент.

Если мы используем паттерн Dependency Injection (DI), мы делегируем создание `RaceService` фреймворку и просто запрашиваем его экземпляр. Фреймворк берет на себя ответственность за создание зависимости и внедряет её:

```javascript
class RaceList {
  constructor(raceService) {
    this.raceService = raceService;
    this.raceService.list().then(races => (this.races = races));
  }
}

```

Теперь при тестировании этого класса мы можем легко передать фейковый сервис в конструктор:

```javascript
// в тесте
const fakeService = {
  list: () => {
    // возвращает фейковый промис
  }
};

const raceList = new RaceList(fakeService);
// теперь мы уверены, что список гонок именно такой,
// какой нам нужен для теста

```

Но как фреймворк узнает, что именно нужно внедрить в конструктор? Отличный вопрос!

AngularJS 1.x полагался на имена параметров, но у этого метода было серьезное ограничение: минификация (сжатие) кода меняла имена параметров... Чтобы исправить это, приходилось использовать синтаксис массивов или добавлять метаданные к классу:

```javascript
RaceList.$inject = ['RaceService'];

```

Нам приходилось явно добавлять метаданные, чтобы фреймворк понимал, какие классы нужно внедрять.

И это именно то, что дают **аннотации типов**: метаданные, дающие фреймворку подсказку, необходимую для правильного внедрения зависимостей.

В Angular с использованием TypeScript мы можем переписать компонент `RaceList` так:

```typescript
class RaceList {
  raceService: RaceService;
  races: Array<string> = [];

  constructor(raceService: RaceService) {
    // Самая интересная часть — `: RaceService`
    this.raceService = raceService;
    this.raceService.list().then(races => (this.races = races));
  }
}

```

Теперь внедрение зависимостей может работать автоматически!

Вот почему мы потратим время на изучение TypeScript (TS). Angular изначально спроектирован так, чтобы использовать все возможности этого языка, поэтому писать приложения на нём будет максимально удобно. А команда Angular очень надеется в будущем подать систему типов на рассмотрение в комитет по стандартизации, чтобы, возможно, однажды типы появились и в самом JS.

Давайте погружаться!
