### Маршрутизатор (Router)

Довольно часто возникает необходимость сопоставить URL со состоянием приложения. Это логично: вы хотите, чтобы пользователь мог добавить страницу в закладки и вернуться к ней позже, а также в целом получить лучший пользовательский опыт. Компонент, отвечающий за эту задачу, называется маршрутизатором (router), и у каждого фреймворка он свой (или даже несколько).

Маршрутизатор в Angular преследует простую цель: создание понятных URL, отражающих состояние нашего приложения, где каждый URL знает, какой компонент должен быть инициализирован и вставлен на страницу. Он выполняет всё это без перезагрузки страницы и без отправки нового запроса на наш бэкенд-сервер — в этом и заключается вся суть одностраничных приложений (Single Page Application, SPA).

Возможно, вы знаете, что в AngularJS 1.x уже был роутер, поддерживаемый основной командой, в модуле под названием `ngRoute`. Вы также можете знать, что он был весьма примитивным: подходил для простых приложений, но позволял отображать только одно представление (view) на один URL, и вложенность была невозможна. Это вызывало ограничения при работе над более крупными приложениями, где часто приходится размещать представления внутри других представлений. Было очень популярное стороннее решение от сообщества под названием `ui-router`, которое использовали многие разработчики и которое отлично справлялось со своей задачей.

Команда Angular решила восполнить этот пробел и написала новый модуль под названием `RouterModule`. Этот модуль полностью закрывает все основные потребности! Некоторые его возможности действительно интересны.

Итак, поехали!

#### 19.1. В путь (provideRouter)

Давайте начнем использовать маршрутизатор.
Это опциональный модуль, который не входит в ядро фреймворка. Как и в случае с HTTP-клиентом, вам нужно предоставить (provide) маршрутизатор в вашем приложении, если вы хотите его использовать.
Но для этого нам нужна конфигурация, определяющая соответствие между URL и компонентами.
Мы можем сделать это в отдельном файле, который обычно называется `app.routes.ts` и содержит массив с конфигурацией:

```typescript
import { Routes } from '@angular/router';
import { Home } from './home/home';
import { Races } from './races/races';

export const routes: Routes = [
  { path: '', component: Home },
  { path: 'races', component: Races }
];

```

Затем нам нужно предоставить маршрутизатор в нашем приложении, инициализировав его соответствующей конфигурацией:

```typescript
import { bootstrapApplication } from '@angular/platform-browser';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';

bootstrapApplication(App, {
  providers: [provideRouter(routes)]
}).catch(err => console.error(err));

```

Как видите, `Routes` — это массив объектов, каждый из которых представляет собой… маршрут (route).
Конфигурация маршрута обычно состоит из пары свойств:

* `path`: какой URL запустит навигацию
* `component`: какой компонент будет инициализирован и вставлен

Вам может быть интересно, куда именно компонент будет вставлен на странице, и это отличный вопрос.
Чтобы компонент был включен в наше приложение (как `Races` в примере выше), мы должны использовать специальный тег в шаблоне основного компонента: `<router-outlet>`.

Это, разумеется, директива Angular, единственная задача которой — служить местом вставки (placeholder) для шаблона компонента текущего маршрута.
Шаблон нашего приложения будет выглядеть так:

```html
<header>
  <nav>...</nav>
</header>
<main>
  <router-outlet />
  <!-- шаблон компонента будет вставлен сюда -->
</main>
<footer>made with &lt;3 by Ninja Squad</footer>

```

При навигации всё остальное останется неизменным (шапка, основное содержимое и футер), а компонент, соответствующий текущему маршруту, будет вставлен сразу после директивы `RouterOutlet`.

Все директивы модуля маршрутизации, включая `RouterOutlet`, являются standalone-директивами. Чтобы использовать их в шаблоне, компонент должен указать их в массиве `imports` своего декоратора. Или же вы можете добавить весь `RouterModule` в `imports`, чтобы сделать все директивы роутера доступными в шаблоне компонента.

#### 19.2. Навигация

Как мы можем перемещаться между различными компонентами?
Что ж, вы можете вручную ввести URL и перезагрузить страницу, но это не очень удобно. И мы не хотим использовать «классические» ссылки с `<a href="…"></a>`. Действительно, клик по такой ссылке заставляет браузер загрузить страницу по этому URL и перезапустить всё Angular-приложение. Но цель Angular как раз и заключается в том, чтобы избежать таких перезагрузок: мы хотим создать Single Page Application.

Разумеется, есть встроенное решение. В шаблоне вы можете вставить ссылку с директивой `RouterLink`, указывающей на путь, куда вы хотите перейти. Директива `RouterLink` может принимать константу, представляющую путь, или массив строк, представляющий путь и его параметры.

Например, в нашем шаблоне `Races`, если мы хотим перейти на главную страницу `Home`, мы можем написать что-то вроде:

```html
<a routerLink="/">Home</a>
<!-- то же самое, что и -->
<a [routerLink]="['/']">Home</a>

```

Во время выполнения значение `href` для ссылки будет вычислено роутером и будет указывать на `/`.

Ведущий слэш (`/`) в пути обязателен. Если его не указать, `RouterLink` построит URL относительно текущего пути (что может быть полезно для вложенных компонентов, как мы увидим позже). Добавление слэша указывает на то, что URL должен рассчитываться от базового URL приложения.

Директиву `RouterLink` можно использовать совместно с директивой `RouterLinkActive`, которая может автоматически устанавливать CSS-класс, если ссылка указывает на текущий активный маршрут. Это позволяет, например, стилизовать пункт меню как выбранный, когда он ведет на текущую страницу:

```html
<a routerLink="/" routerLinkActive="selected-menu">Home</a>

```

Мы даже можем получить ссылку на эту директиву в шаблоне, чтобы узнать, активен ли маршрут:

```html
<a routerLink="/" routerLinkActive #route="routerLinkActive">Home {{ route.isActive ? '(here)' : '' }}</a>

```

Также возможно выполнять навигацию из кода с помощью сервиса `Router` и его метода `navigate()`. Это часто бывает удобно, когда вы хотите перенаправить пользователя после какого-либо действия:

```typescript
export class Races {
  private readonly router = inject(Router);

  protected saveAndMoveBackToHome(): void {
    // ... логика сохранения ...
    this.router.navigate(['']);
  }
}

```

Метод принимает массив параметров, где первым элементом является путь, на который вы хотите перейти.
В URL также можно передавать параметры, что очень полезно для определения динамических URL. Например, мы хотим отобразить страницу с детальной информацией о пони с понятным URL вида `races/id-of-the-race/ponies/id-of-the-pony`.

Для этого давайте определим маршрут в конфигурации с одним (или несколькими) динамическими параметрами:

```typescript
export const routes: Routes = [
  { path: '', component: Home },
  { path: 'races', component: Races },
  { path: 'races/:raceId/ponies/:ponyId', component: Pony }
];

```

Затем мы можем создавать динамические ссылки с помощью `routerLink`:

```html
<a [routerLink]="['/races', raceModel().id, 'ponies', ponyModel().id]">See pony</a>

```

Разумеется, целевому компоненту нужен доступ к этим параметрам, чтобы загрузить и отобразить пони с данным идентификатором. Чтобы получить значение параметров, маршрутизатор предоставляет сервис `ActivatedRoute`, который вы можете внедрить в компонент. У этого объекта есть удобное свойство `snapshot`. В нем содержатся все параметры URL в объекте `paramMap`!

```typescript
export class Pony {
  protected readonly ponyModel: Signal<PonyModel | undefined>;

  constructor() {
    const route = inject(ActivatedRoute);
    const id = route.snapshot.paramMap.get('ponyId')!;
    const ponyService = inject(PonyService);
    this.ponyModel = toSignal(ponyService.get(id));
  }
}

```

Как вы могли заметить, мы используем `snapshot`. Есть ли версия без снимка (`snapshot`)? Да, есть. И она предоставляет способ подписаться на изменения параметров с помощью — вы угадали — `Observable`. Этот Observable называется `paramMap`.

**Это очень важно:** маршрутизатор будет повторно использовать ваш компонент, если сможет!
Предположим, в нашем приложении есть кнопка "Next", чтобы увидеть следующего пони. URL будет меняться, например, с `/ponies/1` на `/ponies/2` при клике пользователя. В этом случае роутер переиспользует существующий экземпляр компонента: это означает, что ни конструктор, ни `ngOnInit` не будут вызваны снова! Если вы хотите, чтобы ваш компонент обновлялся при такой навигации, у вас нет другого выбора, кроме как использовать Observable `paramMap`!

```typescript
export class PonyReusable {
  protected readonly ponyModel: Signal<PonyModel | undefined>;

  constructor() {
    const route = inject(ActivatedRoute);
    const ponyService = inject(PonyService);
    this.ponyModel = toSignal(
      route.paramMap.pipe(
        map((params: ParamMap) => params.get('ponyId')!),
        switchMap(id => ponyService.get(id))
      )
    );
  }
}

```

Здесь мы подписываемся на Observable, предоставляемый `ActivatedRoute`. Теперь каждый раз, когда URL меняется, например, с `/ponies/1` на `/ponies/2`, Observable `paramMap` будет генерировать событие, и мы заново запросим нужного пони для отображения на экране.

Попробуйте наше упражнение **Router**, чтобы научиться настраивать маршрутизатор, перемещаться между компонентами и тестировать всё это.

То, что вы только что узнали, должно покрыть ваши базовые потребности в маршрутизации. Но роутер выходит далеко за эти рамки и предлагает множество дополнительных возможностей. Подробный разбор всех их — довольно большая задача. В этом разделе мы постараемся представить большинство дополнительных функций как можно более лаконично, объяснив, для чего они полезны.

#### 19.3. Редиректы

Распространенный сценарий — когда один URL должен просто перенаправлять на другой URL в приложении. Это может потребоваться, например, если вы хотите, чтобы корневой URL вашего новостного приложения перенаправлял на категорию `/breaking`, или старый URL перенаправлял на новый после рефакторинга. Это делается с помощью:

```typescript
{ path: '', pathMatch: 'full', redirectTo: '/breaking' },

```

#### 19.4. Стратегия сопоставления

В приведенном выше примере с редиректом я применил стратегию сопоставления маршрута `'full'`. Стратегия по умолчанию — `'prefix'`, которая считает маршрут совпадающим, если URL начинается с пути маршрута. Если бы мы использовали стратегию по умолчанию здесь, все URL перенаправлялись бы на `/breaking`, так как любой URL начинается с пустой строки.

Стратегия сопоставления заключается в поиске *первого* маршрута, который полностью соответствует URL. Например, если вы определите маршруты следующим образом:

```typescript
{ path: 'races/:id', component: Race },
{ path: 'races/new', component: RaceCreation }

```

и перейдете по URL `races/new`, компонент, который активирует маршрутизатор, на самом деле будет `Race`. Дело в том, что `races/:id` совпадает с `races/new` и идет первым в списке маршрутов. Чтобы решить эту проблему, измените порядок маршрутов:

```typescript
{ path: 'races/new', component: RaceCreation },
{ path: 'races/:id', component: Race }

```

#### 19.5. Иерархические маршруты и маршруты с пустым путем

Маршруты могут иметь дочерние элементы (`children`). Это полезно по нескольким причинам:

* применение гардов (guards) к нескольким маршрутам одновременно (см. далее);
* применение резолверов (resolvers) к нескольким маршрутам одновременно (см. далее);
* использование общего шаблона несколькими маршрутами.

Как мы видели ранее, когда маршрутизатор активирует маршрут, компонент маршрута вставляется на страницу в месте, отмеченном директивой `<router-outlet>`.
Этот механизм также можно использовать во вложенных компонентах.
Предположим, у вас есть сложная страница для отображения профиля пони. На этой странице вверху отображается его имя и портрет, а внизу есть несколько вкладок: одна для свидетельства о рождении, одна для спортивных достижений и одна для отзывов журналистов. Вы хотите иметь отдельный URL для каждой вкладки, чтобы иметь возможность давать на них прямые ссылки. Но вы не хотите перезагружать данные пони и дублировать его имя и портрет в каждом из этих трех компонентов вкладок.

Решение состоит в том, чтобы использовать вложенный `<router-outlet>` в шаблоне компонента `Pony` и определить родительский маршрут пони следующим образом:

```typescript
{
  path: 'ponies/:ponyId',
  component: Pony,
  children: [
    { path: 'birth-certificate', component: BirthCertificate },
    { path: 'track-record', component: TrackRecord },
    { path: 'reviews', component: Reviews }
  ]
}

```

При переходе по URL `ponies/42/reviews`, например, маршрутизатор вставит `Pony` в место, указанное основным `<router-outlet>` в корневом компоненте. Шаблон `Pony`, помимо имени и портрета пони, содержит второй `<router-outlet>`. Именно туда будет вставлен дочерний компонент `Reviews`.

При переходе по URL `ponies/42` будет отображен компонент `Pony`, но ни один из трех дочерних компонентов отображен не будет. Вы можете захотеть отображать вкладку свидетельства о рождении по умолчанию. Этого можно добиться с помощью маршрута с пустым путем, перенаправляющего на маршрут `birth-certificate`:

```typescript
{
  path: 'ponies/:ponyId',
  component: Pony,
  children: [
    { path: '', pathMatch: 'full', redirectTo: 'birth-certificate' },
    { path: 'birth-certificate', component: BirthCertificate },
    { path: 'track-record', component: TrackRecord },
    { path: 'reviews', component: Reviews }
  ]
}

```

Обратите внимание, что в приведенном выше примере редирект выполняется относительно маршрута `ponies/:ponyId`, поскольку он не начинается с `/`.

Вместо перенаправления вы можете захотеть сразу отображать свидетельство о рождении по URL `ponies/42`. Это также можно сделать с помощью дочернего маршрута с пустым путем:

```typescript
{
  path: 'ponies/:ponyId',
  component: Pony,
  children: [
    { path: '', component: BirthCertificate },
    { path: 'track-record', component: TrackRecord },
    { path: 'reviews', component: Reviews }
  ]
}

```

#### 19.6. Гарды (Guards)

Некоторые маршруты приложения не должны быть доступны всем пользователям в зависимости от их прав. Конечно, вам следует скрывать или отключать ссылки на эти маршруты, если пользователю запрещен доступ. Вы также должны убедиться, что бэкенд не позволяет получать доступ к ресурсам или изменять их без авторизации. Но это все равно не помешает пользователям вводить URL в адресной строке.

Именно здесь вступают в игру гарды (guards). Существует 4 типа гардов:

* `canActivate`: при установке на маршрут может запретить активацию этого маршрута. Обратите внимание, что гард также может вернуть URL для перенаправления в другое место (а точнее, тип Angular под названием `UrlTree`). Это полезно для показа страницы ошибки или перенаправления на страницу входа, если неавторизованный пользователь пытается получить доступ к защищенному маршруту.
* `canActivateChild`: при установке на маршрут может запретить активацию дочерних маршрутов. Это полезно для ограничения доступа сразу к группе дочерних маршрутов.
* `canDeactivate`: отличается от остальных. Он используется для предотвращения ухода с текущего активного маршрута. Это полезно, например, для запроса подтверждения перед покиданием страницы с несохраненной большой формой.
* `canMatch`: появился в Angular v14.1. Он указывает маршрутизатору, может ли данный маршрут быть сопоставлен с URL или нет. Если гард возвращает `false`, маршрут просто игнорируется, и роутер ищет следующий подходящий маршрут. Типичное использование `canMatch` — иметь несколько маршрутов с одинаковым путем, но разными компонентами, и выбирать нужный на основе профиля пользователя.

Вот как добавить гард `canActivate` к маршруту (остальные три добавляются аналогично):

```typescript
{ path: 'races', component: Races, canActivate: [loggedInGuard] }

```

В приведённом примере `loggedInGuard` — это функция.

В ранних версиях Angular (до v15.2) гарды определялись как сервисы, но сейчас этот подход устарел.
Функция решает, может ли маршрут быть активирован (например, проверяя, вошел ли пользователь в систему), и возвращает `boolean`, `Promise<boolean|UrlTree>`, `Observable<boolean|UrlTree>` или `UrlTree`.
Маршрутизатор перейдет по маршруту, если возвращаемое значение равно `true` (или промис/observable резолвится в `true`). Если возвращается `UrlTree`, текущая навигация отменяется, и запускается переход по переданному `UrlTree`.

Вот как может выглядеть функция `loggedInGuard`:

```typescript
export const loggedInGuard: CanActivateFn = (
  _route: ActivatedRouteSnapshot,
  _state: RouterStateSnapshot): boolean | UrlTree => {
  const userService = inject(UserService);
  const router = inject(Router);
  // возвращает `true`, если пользователь авторизован, или перенаправляет на страницу входа
  // обратите внимание, что вы также можете использовать `router.createUrlTree()` для сборки `UrlTree` с параметрами
  return userService.isLoggedIn() || router.parseUrl('/login');
};

```

Иерархические маршруты в комбинации с пустыми путями очень удобны, когда нужно применить гард сразу к нескольким маршрутам. Например, если вы хотите сделать маршруты `races` и `ponies` доступными только авторизованным пользователям, вместо:

```typescript
{ path: 'ponies/:ponyId', component: Pony, canActivate: [loggedInGuard] },
{ path: 'races', component: Races, canActivate: [loggedInGuard] }

```

вы можете ввести родительский маршрут с пустым путем и без компонента. Этот маршрут не будет занимать сегменты URL и не активирует компонент, но его гарды будут вызываться при переходе к любому из дочерних элементов:

```typescript
{
  path: '',
  canActivate: [loggedInGuard],
  children: [
    { path: 'ponies/:ponyId', component: Pony },
    { path: 'races', component: Races }
  ]
}

```

#### 19.7. Резолверы (Resolvers)

В старых добрых многостраничных приложениях, где страницы генерируются на стороне сервера, при клике по ссылке происходит следующее: запрос отправляется на сервер, браузер показывает индикатор загрузки на вкладке, и когда ответ возвращается, URL в адресной строке меняется и отображается новая страница.

В одностраничном Angular-приложении это работает не совсем так. Пользователь кликает по ссылке, чтобы посмотреть гонку. Роутер создает экземпляр компонента `Race`, и компонент отправляет AJAX-запрос для загрузки данных. Роутер сразу же вставляет шаблон компонента в `<router-outlet>` и меняет URL в адресной строке. В этот момент пользователь видит новую страницу, но пока без данных о гонке. Когда AJAX-ответ возвращается, данные сохраняются в компоненте, и DOM обновляется.

У этого подхода есть свои плюсы и минусы:

* навигация ощущается более быстрой;
* пользователь может быть запутана, если загрузка длится долго, так как страница пуста (что похоже на баг);
* шаблон должен быть написан аккуратно, чтобы корректно обрабатывать время, пока модель равна `null` или `undefined`;
* шаблон может сразу показывать спиннер загрузки;
* если загрузка не удалась (например, пропала связь), навигация уже состоялась и URL изменился, хотя страница не может показать данные.

Резолвер (Resolver) позволяет приложению вести себя почти как традиционное многостраничное приложение. Вместо того чтобы заставлять компонент самостоятельно загружать данные, вы привязываете резолвер к маршруту, и он загружает данные до активации компонента.

Как и гард, резолвер может возвращать данные синхронно или асинхронно (в виде `Promise` или `Observable`). Маршрутизатор выполнит переход только после того, как промис зарезолвится или Observable завершится (completed) хотя бы с одним значением.

Вот как выглядит резолвер для гонки:

```typescript
export const raceResolver: ResolveFn<RaceModel> = (route: ActivatedRouteSnapshot): Observable<RaceModel> => {
  const id = route.paramMap.get('raceId')!;
  const raceService = inject(RaceService);
  return raceService.get(id);
};

```

Это простая функция, которая использует снимок маршрута `ActivatedRouteSnapshot` для получения `raceId` и возвращает `Observable<RaceModel>`.

Применение резолвера к маршруту:

```typescript
{
  path: 'races/:raceId',
  component: Race,
  resolve: {
    race: raceResolver
  }
}

```

Резолвер связывается с ключом объекта (в данном случае `race`). Под этим ключом загруженные данные сохраняются в `data` объекта `ActivatedRouteSnapshot`. Компонент может получить эти данные следующим образом:

```typescript
export class Race {
  protected readonly race = signal(inject(ActivatedRoute).snapshot.data['race']);
}

```

Обратите внимание: если вы переходите с маршрута на тот же маршрут, но с другими параметрами (например, ссылка "Следующая гонка"), гарды и резолверы будут вызваны снова. Компонент при этом переиспользуется, поэтому лучше подписаться на Observable с данными:

```typescript
export class Race {
  private readonly route = inject(ActivatedRoute);
  protected readonly raceModel = toSignal(this.route.data.pipe(map(data => data['race'])));
}

```

Резолверы имеют много преимуществ перед загрузкой данных непосредственно из активированного компонента:

* делают навигацию более традиционной;
* могут переиспользоваться между несколькими маршрутами;
* упрощают код компонента и шаблона (не нужно загружать данные и обрабатывать состояния `null`/`undefined`);
* если загрузка завершилась ошибкой, пользователь остается на текущей странице и может попробовать снова.

Единственный минус: при медленной загрузке данных приложение может показаться независающим — пользователь кликает на ссылку, и ничего не происходит, пока данные не загрузятся. В таких случаях можно использовать события роутера для показа индикатора загрузки.

#### 19.8. События роутера

Маршрутизатор эмитит несколько событий в процессе навигации. Вы можете подписываться на них через сервис `Router` и его Observable `events`. Типы событий можно фильтровать с помощью `event instanceof NavigationStart`.

Основные типы событий:

* `NavigationStart`: эмитится при старте навигации (например, при клике на ссылку). Полезно для старта показа спиннера.
* `NavigationEnd`: эмитится при успешном завершении навигации. Используется для скрытия спиннера или отправки аналитики (Google Analytics).
* `NavigationError`: эмитится при неожиданной ошибке навигации (например, упал резолвер).
* `NavigationCancel`: эмитится, если навигация была отменена (например, гардом).

Также есть события загрузки конфигурации (`RouteConfigLoadStart`, `RouteConfigLoadEnd`, `RoutesRecognized`), проверок гардов и резолверов (`GuardsCheckStart`, `ResolveStart` и т. д.), детальные события активации дочерних элементов (`ChildActivationStart`), а также события прокрутки (`Scroll`).

#### 19.9. Параметры и данные

Маршруты могут иметь параметры. Например, `races/:raceId` содержит параметр `raceId`. Но роутер также поддерживает **матричные параметры** (matrix parameters).

Матричные параметры — это часть стандарта URI (например, `/races/42;foo=bar;baz=wiz`). Значения `foo` и `baz` будут доступны в `params` и `paramMap` конкретного активированного сегмента маршрута.

Для перехода по такому URL используется код:

```typescript
router.navigate(['/races', 42, { foo: 'bar', baz: 'wiz' }, 'ponies']);

```

Или в шаблоне:

```html
<a [routerLink]="['/races', 42, { foo: 'bar', baz: 'wiz' }, 'ponies']">Link</a>

```

**Query-параметры** (параметры запроса) разделяются между всеми сегментами маршрута (`/races/42/ponies?foo=bar&baz=wiz`) и доступны через `queryParams` / `queryParamMap`:

```typescript
router.navigate(['/races', 42, 'ponies'], { queryParams: { foo: 'bar', baz: 'wiz' } });

```

```html
<a [routerLink]="['/races', 42, 'ponies']" [queryParams]="{ foo: 'bar', baz: 'wiz' }">Link</a>

```

Также можно передавать статические данные в конфигурации маршрута через свойство `data`:

```typescript
{
  path: 'races',
  component: Races,
  data: {
    allowDeletion: false
  }
}

```

#### 19.10. Привязка параметров и данных к инпутам компонента

Начиная с Angular v16, параметры и данные маршрута можно автоматически привязывать к `input`-свойствам компонента.
Для этого нужно включить опцию `withComponentInputBinding()` при настройке роутера в `app.config.ts`:

```typescript
provideRouter(routes, withComponentInputBinding())

```

Теперь компонент может объявить `input` с таким же именем, как у параметра или свойства `data`:

```typescript
export class Race {
  readonly raceId = input.required<string>();

```

И использовать его как обычный инпут, реагируя на изменения с помощью `toObservable` и `toSignal`:

```typescript
private readonly raceService = inject(RaceService);
private readonly raceModel$ = toObservable(this.raceId).pipe(switchMap(id => this.raceService.get(id)));
protected readonly raceModel = toSignal(this.raceModel$);

```

#### 19.11. Ленивая загрузка (Lazy loading)

Ленивая загрузка заключается в разделении приложения на несколько JavaScript-бандлов и их загрузке по требованию.

Вместо импорта всех компонентов сразу, роутер использует `loadChildren` или `loadComponent` с динамическими импортами TypeScript.

1. Создаем файл маршрутов для ленивого модуля (например, `admin.routes.ts`):

```typescript
export const adminRoutes: Routes = [{ path: '', component: Admin }];

```

2. Подключаем его в главном `app.routes.ts`:

```typescript
{ path: 'admin', loadChildren: () => import('./admin/admin.routes').then(m => m.adminRoutes) }

```

Если файл использует `export default`, импорт можно упростить:

```typescript
{ path: 'admin', loadChildren: () => import('./admin/admin.routes') }

```

А если нужно загрузить только один компонент без отдельного файла маршрутов:

```typescript
{ path: 'admin', loadComponent: () => import('./admin/admin').then(m => m.Admin) }

```

Angular CLI автоматически выделит эти компоненты в отдельные бандлы (чанки) и загрузит их, когда пользователь перейдет по соответствующему URL.
