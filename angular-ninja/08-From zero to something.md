### От нуля к чему-то большему

Давайте начнём с создания нашего первого приложения на Angular и нашего первого компонента с минимальным набором инструментов.

---

### 8.1. Node.js и NPM

В наши дни практически все современные инструменты JavaScript разрабатываются для экосистемы Node.js и NPM. Вам потребуется установить Node.js и NPM в свою систему. Наиболее подходящий способ установки зависит от вашей операционной системы — подробную информацию можно найти на официальном сайте.

Убедитесь, что у вас установлена достаточно свежая версия Node.js (выполнив команду `node --version`).

---

### 8.2. Angular CLI

Вы могли бы настроить всё самостоятельно, начиная с пустого TypeScript-проекта, затем установив все необходимые зависимости и т.д. Но в реальном проекте вам, скорее всего, придется настроить и множество других вещей:

* тесты, чтобы убедиться, что изменения ничего не ломают;
* линтер для проверки качества кода;
* CSS-препроцессор;
* инструмент сборки для оркестрации задач (компиляция, тестирование, упаковывание и т.д.).

Но настраивать всё вручную довольно хлопотно, особенно когда существует *такое* количество инструментов, с которыми нужно сначала разобраться.

В последние годы появилось много генераторов небольших проектов, большинство из которых использовали Yeoman. Так было во времена AngularJS 1.x, и со стороны сообщества предпринимались попытки сделать нечто подобное для Angular. Но на этот раз команда Google взялась за задачу сама и создала **Angular CLI**.

**Angular CLI** — это консольная утилита для быстрого старта проекта, заранее настроенная с применением современных инструментов (Vite для сервера разработки, быстрых сборок, тестов, упаковки и т.д.). Идея не нова и на самом деле заимствована из другого популярного фреймворка: EmberJS и его высокооценённого `ember-cli`. Инструмент непрерывно развивается: выделенная команда Google работает над ним, постоянно его улучшая. Сегодня это рекомендуемый и являющийся стандартом де-факто способ создания и сборки Angular-приложений.

Так давайте же попробуем его в деле и откроем для себя кучу запакованных в него крутых фич!

Сначала давайте установим Angular CLI глобально и сгенерируем новое приложение с помощью команды `ng new`. Если вы хотите использовать ту же версию CLI, что и мы (21.1.4), вы можете запустить `npm install -g @angular/cli@21.1.4`.

```bash
npm install -g @angular/cli

ng new ponyracer --defaults --no-routing --prefix ns

```

Эта команда создаст каркас проекта в новой директории `ponyracer`. Перейдя в эту директорию, вы можете запустить приложение:

```bash
ng serve

```

Команда запустит локальный HTTP-сервер с настроенной горячей перезагрузкой (hot reload). Это означает, что при каждом изменении и сохранении файла сервер пересоберет приложение, а браузер мгновенно обновит страницу.

Тадам! Ваше первое приложение запущено и работает! 🎉

> В Angular 15 фреймворк представил новую фичу — **автономные компоненты** (*standalone components*), которые стали выбором по умолчанию начиная с Angular v17.
> До этого компоненты должны были объявляться в модулях Angular (NgModules) — достаточно сложной для понимания концепции, особенно при старте работы с фреймворком. Использование standalone-компонентов позволяет избежать создания модулей Angular и делает многие вещи проще, особенно для новичков. Автономные компоненты — это путь в будущее, поэтому мы выбрали именно этот вариант.
> Мы всё равно объясним модули Angular в одной из следующих глав, так как вам потребуется понимать их назначение при работе с существующим кодом, но пока о них можно не беспокоиться.

### 8.3. Бандлеры: Webpack, Rollup, esbuild

При написании современных приложений на JavaScript/TypeScript часто нужен инструмент, способный объединить (упаковать) все ресурсы приложения (код, стили, изображения, шрифты) в единые бандлы.

Долгое время безраздельным лидером был **Webpack**. Webpack обладает простой, но невероятно полезной особенностью: он понимает все существующие типы модулей JavaScript (современные ECMAScript-модули, а также существовавшие до стандарта форматы AMD или CommonJS). Благодаря этому легко использовать практически любую библиотеку из интернета (чаще всего из NPM): вы просто устанавливаете её, импортируете в один из своих файлов, а Webpack берёт всё остальное на себя. Даже если библиотеки используют совершенно разные форматы модулей, Webpack конвертирует их и упаковывает весь ваш код вместе с кодом библиотек в один гигантский JS-файл — бандл (*bundle*).

Вторая задача Webpack — помощь при разработке: предоставление dev-сервера и отслеживание изменений в файлах (он умеет выполнять даже HMR — Hot Module Reloading). Когда что-то меняется, Webpack читает точку входа приложения (например, `main.ts`), затем считывает его импорты и загружает эти файлы, затем считывает импорты импортированных файлов и т.д. Когда всё загружено, он пересобирает всё в один файл, обновляя формат модулей при необходимости. После этого браузер перезагружает страницу 😅. Это может занимать много времени на крупных проектах с сотнями или тысячами файлов, даже несмотря на то, что Webpack использует кэширование и эвристику для ускорения.

Angular CLI годами использовал Webpack как для сборок, так и для dev-сервера. Это было отлично, так как экосистема Webpack невероятно богата плагинами и лоадерами. С другой стороны, конфигурация Webpack с её изобилием опций может быстро стать сложной и запутанной.

Если я говорю о Webpack и бандлерах, то только потому, что сегодня существуют серьезные альтернативы, и иногда трудно понять, что они делают и чем отличаются.

Серьезный конкурент — **Rollup**. Rollup стремится быть проще Webpack: он делает меньше «из коробки», но часто выполняет сборку быстрее. Его автор — Рич Харрис (Rich Harris), который также создал фреймворк Svelte. Рич написал знаменитую статью *«Webpack and Rollup: the same but different»*. Его главный принцип: *«Используйте Webpack для приложений, а Rollup — для библиотек»*. На самом деле Rollup способен выполнять многое из того, что делает Webpack для продакшн-сборок, но он не поставляется со встроенным dev-сервером для отслеживания изменений в процессе разработки.

Ещё одна невероятная альтернатива — **esbuild**. В отличие от Webpack и Rollup, сам esbuild написан не на JavaScript. Он написан на Go и скомпилирован в нативный код, а также спроектирован с расчётом на параллельные вычисления. Это делает его быстрее Webpack и Rollup в 10–100 раз 🤯.

Так почему бы нам просто не использовать esbuild вместо Webpack? Именно эта мысль и привела к взлету **Vite**.

---

### 8.4. Vite

Идея Vite заключается в том, что современным браузерам больше не нужна сборка приложения в один бандл на этапе разработки — они нативно поддерживают ES-модули.

Когда вы загружаете страницу в браузере при разработке с Vite, вы не загружаете один огромный JS-файл: загружаются только те несколько ES-модулей, которые необходимы для текущей страницы, каждый в своем файле (и по отдельному HTTP-запросу). Если у ES-модуля есть импорты, браузер сам последовательно подгружает и их.

Поэтому Vite — это в первую очередь dev-сервер, который отвечает на запросы браузера и отдаёт нужные ES-модули. Так как мы пишем код на TypeScript, Vite транслирует файлы с диска в валидные ES-модули, понятные браузеру. И здесь в игру вступает **esbuild**! Vite построен поверх esbuild, и когда файл нужно преобразовать, он поручает эту работу esbuild, после чего отправляет результат в браузер.

Если вы меняете что-то в файле, Vite отправляет в браузер *только обновленный модуль*, вместо пересборки всего бандла, как это делают инструменты на базе Webpack!

Vite также использует esbuild для оптимизации. Например, если вы используете библиотеку с множеством файлов, Vite «предварительно сжимает» (pre-bundles) её в один файл с помощью esbuild и отдаёт браузеру за один запрос. Пре-бандлинг выполняется один раз при запуске сервера, поэтому вам не нужно платить за него временем при каждом обновлении страницы.

esbuild очень хорош в сборке JS, но он пока не способен правильно разбивать приложение на несколько бандлов (code splitting) или полноценно обрабатывать CSS (в то время как Webpack и Rollup делают это из коробки). Поэтому он не идеально подходит для финальной продакшн-сборки.

Здесь вступает **Rollup**: Vite полагается на esbuild во время разработки, но использует Rollup для продакшн-сборки по умолчанию.

В наши дни Angular CLI под капотом использует Vite для `ng serve` и собственный пайплайн для продакшн-сборок (`ng build`), при этом задействуя оптимизации компилятора Angular.

### 8.5. Структура приложения

Давайте на несколько секунд заглянем в сгенерированный код. Откройте проект в вашей любимой IDE (WebStorm, Visual Studio Code или любой другой с поддержкой TypeScript).

Благодаря файлам типов (`.d.ts`), расположенным в папке `node_modules`, в IDE будет работать автодополнение кода, а TypeScript обеспечит проверку типов прямо во время ввода. А за счёт source maps вы сможете отлаживать оригинальный TypeScript-код прямо в браузере, расставляя точки останова (breakpoints).

В корневой директории вы увидите служебные конфигурационные файлы:

* `package.json` — описывает зависимости приложения (пакеты `@angular`, `rxjs`, `zone.js`, инструменты разработки и линтеры).
* `tsconfig.json` (и `tsconfig.app.json`) — содержит параметры компиляции TypeScript (например, поддержку декораторов и генерацию source maps).
* `angular.json` — конфигурационный файл самого Angular CLI.

### 8.6. Наш первый автономный компонент (Standalone Component)

Компонент представляет собой комбинацию представления (шаблона) и логики (TS-класса). CLI уже создал один компонент для нас в файле `src/app/app.ts`:

`app.ts`

```typescript
import { Component, signal } from '@angular/core';

@Component({
  selector: 'ns-root',
  templateUrl: './app.html',
  styleUrl: './app.css'
})
export class App {
  protected readonly title = signal('ponyracer');
}

```

Само наше приложение — это простой компонент. Чтобы сказать Angular, что класс является компонентом, мы используем декоратор `@Component`, импортированный из `@angular/core`.

Декоратор `@Component` принимает объект конфигурации:

1. `selector` — сообщает Angular, какой HTML-тег искать в разметке. Каждый раз, когда Angular видит элемент `<ns-root />`, он создаёт экземпляр класса `App` и вставляет его шаблон.
> **Именование селекторов:**
> Angular рекомендует использовать префикс в селекторах компонентов во избежание конфликтов имён. При создании проекта с помощью `ng new --prefix ns` мы настроили CLI на генерацию компонентов с префиксом `ns-` (например, `ns-pony`).


2. `templateUrl` — путь к файлу шаблона (`app.html`).
`app.html`
```html
<h1>Hello, {{ title() }}</h1>
<p>Congratulations! Your app is running. 🎉</p>

```


3. `imports` — массив импортов для компонента.
`app.ts`
```typescript
import { Component, signal } from '@angular/core';

@Component({
  selector: 'ns-root',
  imports: [],
  templateUrl: './app.html',
  styleUrl: './app.css'
})
export class App {
  protected readonly title = signal('ponyracer');
}

```



Наш компонент является **автономным** (*standalone* — это поведение по умолчанию начиная с Angular v19). Это означает, что его не нужно объявлять в NgModule.

Свойство `imports: []` указывает Angular, какие *другие* компоненты, пайпы (pipes) и директивы могут быть использованы внутри шаблона этого компонента. Если бы Angular встретил элемент `<ns-race>` внутри шаблона `App`, нам потребовалось бы добавить компонент `Race` в массив `imports` декоратора `App`.

### 8.7. Запуск приложения (Bootstrapping)

В завершение нам нужно запустить приложение с помощью функции `bootstrapApplication`. По умолчанию Angular CLI генерирует отдельный файл с этой логикой — `main.ts`:

`main.ts`

```typescript
import { bootstrapApplication } from '@angular/platform-browser';
import { appConfig } from './app/app.config';
import { App } from './app/app';

bootstrapApplication(App, appConfig)
  .catch((err) => console.error(err));

```

Функция ожидает передачи корневого компонента приложения — `App`.

Но как всё это отображается пользователю? CLI создал файл `index.html` — единственную HTML-страницу нашего одностраничного приложения (SPA). Когда вы запускаете `ng serve`, CLI компилирует TypeScript, бандлит его (используя Vite под капотом) и автоматически внедряет необходимые скрипты в `index.html`.

Теперь вы лучше понимаете, из чего состоит первое приложение на Angular. Пока оно не слишком динамическое, но в следующих разделах мы подробно изучим сигналы (signals) и синтаксис шаблонов!
